## 3. Decisions and rationale

1. **Generated vs checked.** A table that is purely a function of the code is generated. Prose that
   quotes a figure is checked.

   | Artifact | Where | Mechanism |
   |---|---|---|
   | One-person worked examples | LIVABILITY §1 | **generated**: block `juice-worked-examples/single` |
   | By-household table (the San Francisco $675K case first) | LIVABILITY §1 | **generated**: `…/household` |
   | Score legend: grade table and "Other legend points" | LIVABILITY §1 | **generated**: `…/score-legend` |
   | Tax-source table (one row per `TAX_SOURCES` key, 69 rows) | LIVABILITY §3 | **generated**: `…/tax-sources`. The hand-edited header ("Verified 2026-10-02") is kept. |
   | Inline counts and constants in LIVABILITY and CONTRACT | 32 rules | **checked**: `docs-counts`, detect |
   | README counts, lists and constants | 14 rules | **checked**: `readme-counts`, detect |
   | Calibration paragraph and table (real snapshots of 2026-10-02) | LIVABILITY §1 | **checked + manual**: K must match the code; a staleness date |
   | Methodology reference page | dist/methodology/ | **checked**: renders the doc; markers must not show; anchors and tables present |
   | Share card | public/og/ | **checked + manual**: see decision 5 |
   | Share pages | dist/c/<slug>/ | already **regenerated by every Pages build** (pipeline) |
   | Tests pinning data | test/e2e, test/juice.test.js | **checked**: `e2e-pinned-values`, plus a patch that makes them robust |

   Dated records are left alone on purpose: docs/QA.md, docs/REVIEW.md, docs/VETTING.md tuning
   notes, docs/DATA_SOURCES.md observations, docs/strategy/*, docs/process/*. Each carries its own
   date, and rewriting them would lose history.

2. **Marker format.** A block is wrapped like this:

   ```
   <!-- freshness:begin <registry id>/<block> -->
   (blank line)
   ...generated...
   (blank line)
   <!-- freshness:end <registry id>/<block> -->
   ```

   - The markers are whole-line HTML comments. GitHub hides them, and they interrupt a paragraph
     or table cleanly.
   - Inline markers were rejected: they are noisy, and md.js would need inline comment handling too.
   - Unknown or unbalanced markers return `error`, so a typo never passes silently.

3. **Markers absent means detect.** Until the marker patch lands, `juice-worked-examples` compares
   the hand-written tables row by row with the generated ones and reports `drift`. The module is
   therefore useful today, and it caught the tax agent's in-progress change: 91 differing rows at
   08:20Z, 20 at 08:45Z.

4. **The overlay.** derived.js runs last (`MODULE_ORDER`) and imports `server/juice.js` and
   `server/geo.js` from the orchestrator's overlay: it copies them to a temp dir and imports them
   from there. If fx.js has just rewritten `FX_PER_USD` in juice.js, the regenerated examples use
   the new rates. Without this they would lag a month.

5. **OG card.**
   - The card's numbers are illustrative by design: card.html says so, and no company is named.
     Putting real counts on a committed PNG would make it stale within a day. Per-company numbers
     already sit in the share pages' text, which every build regenerates.
   - Decision: the card stays illustrative. The registry entry is manual with a yearly review.
     derived.js checks the following:
     - the disclaimer is present;
     - the headline count equals the sum of the rows (214 = 64 + 88 + 27 + 35);
     - the PNG is 1200x630 and under 5 MB;
     - the sha256 of card.html and of the PNG equal the render manifest
       `test/fixtures/refresh/derived/og-render.json`. A change to card.html without a re-render
       shows as `drift`.
   - Chromium in CI: ubuntu-latest has Chromium 154 (see §2), so the monthly workflow could run
     scripts/build-og.mjs with `playwright-core` installed outside the repo
     (`npm i --prefix "$RUNNER_TEMP/pw" playwright-core`) and
     `CHROMIUM_PATH=/usr/local/share/chromium/chrome-linux/chrome`.
   - Not automated: an illustrative card gains nothing from a monthly render, and Chromium renders
     are not byte-stable, so every run would open a PR. The checklist has the exact commands.

6. **Pinned tests.**
   - test/juice.test.js pinned `DOC.bigMac.asOf === '2026-07-01'`. It fails the first time the
     monthly Big Mac refresh lands. The patch makes it relational: the value read before the call.
   - Three e2e tests open the real posting `anthropic:5391376008`. The patch keeps the pin while
     the posting is listed, then falls back to a current Anthropic job without pay (Senior,
     London, else any).
   - Everything else that pins values is an intentional golden vector, listed in the registry
     entry's notes:
     - tax golden tests;
     - fixture-based source tests;
     - the BLS/MIT living-scale cross-checks;
     - the og.test.js 4-role fixture.

7. **"As of" design (registry first, data second).**
   - `publicFreshness(registry)` is the client-safe subset:
     - id, description, type, asOf, taxYear, source { name, url }, cadence, lastChecked;
     - `stale` at build time, and `staleAfter`: the last fresh day, so the browser judges
       staleness on the viewer's clock.
   - No owners, checklists or notes are published. The output is always a document; without a
     registry it is `entries: []` and `missing: true`. A 404 would be an e2e error, because the
     suite counts any same-origin response ≥ 400.
   - In the drawer's Juice block:
     - **FX and each tax line** come from the registry: `fx-per-usd`, and `tax-<key>`'s taxYear;
     - **rent and living costs** show the city record's own date (cities.json, which varies by
       city: 2026-05 to 2026-10). The family entry's single asOf would be wrong for most cities,
       so its job there is the "update due" flag.
   - Juice rent ids:
     - `rents-1br-quoted` for one bedroom, plus `rents-bedroom-ratios` for two or three;
     - `rents-nsw-official` for an official NSW source.
   - Living costs use `cost-index` and `nyc-basket`, plus `living-scale` for couple or family.
   - Ids follow the lead's canonical list.
   - The registry is lazy-loaded; a label renders at once from the data's own dates and is
     upgraded when the registry arrives.
